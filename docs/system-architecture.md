# TicketFlow: системный контур

## Цель

Построить единую систему обмена документами между:

- `sirena-olt-client`
- FTP
- MOM (cloud service)
- SMB / сервером 1С

Система должна:

- автоматически перемещать документы между узлами;
- хранить историю всех файлов и их состояний;
- показывать жизненный цикл каждого документа в веб-интерфейсе;
- связывать `ticket`, `realization` и `payment` между собой;
- вести резервные копии файлов, метаданных и событий.

## Потоки

### 1. Билеты

`sirena-olt-client -> FTP(tickets) -> MOM`

Источник:

- `/opt/sirena-olt-client/received-files`

Промежуточный обмен:

- `/srv/ftp/tickets`
- `/srv/ftp/tickets/processed`
- `/srv/ftp/tickets/error`

### 2. Реализации

`MOM -> FTP(realizations) -> SMB(1C)`

Источник:

- `/srv/ftp/realizations`

Назначение:

- SMB-шара сервера 1С

### 3. Платежки

`SMB(1C) -> FTP(payments) -> MOM`

Источник:

- `/srv/ftp/payments`
- `/srv/ftp/payments/processed`
- `/srv/ftp/payments/error`

## Основной принцип

Система должна работать как трекер документов и оркестратор доставки:

- обнаруживать новый файл;
- рассчитывать его хэш;
- распознавать тип документа;
- извлекать бизнес-данные;
- сохранять файл в архив;
- проводить доставку на следующий этап;
- фиксировать каждое событие с точным временем;
- отображать все этапы в UI.

## Авторизация и роли

Авторизация обязательна.

В системе две роли:

- `admin`
- `user`

### Права `admin`

- вход в систему;
- просмотр всех документов и событий;
- работа со всеми фильтрами и периодами;
- просмотр ошибок;
- скрытие ошибок как просмотренных;
- повторный запуск обработки;
- создание пользователей;
- создание администраторов;
- редактирование и деактивация учетных записей.

### Права `user`

- вход в систему;
- просмотр всех документов и событий;
- работа со всеми фильтрами и периодами;
- просмотр ошибок;
- скрытие ошибок как просмотренных;
- повторный запуск обработки;
- весь функционал приложения, кроме управления учетными записями.

### Требования к авторизации

- логин по имени пользователя и паролю;
- хранение паролей только в виде безопасного хэша;
- сессия через JWT access token и refresh token или серверную session-cookie;
- принудительный logout при деактивации пользователя;
- аудит входов, выходов и действий администратора.

### Требования к управлению пользователями

Админ в веб-интерфейсе должен иметь раздел:

- список пользователей;
- создание пользователя;
- создание администратора;
- смена роли;
- деактивация учетной записи;
- сброс пароля.

### Инфраструктура

- systemd для запуска сервисов
- Nginx как reverse proxy
- локальное файловое хранилище для архивов и бэкапов
- PostgreSQL для реестра документов и событий

## Компоненты системы

### 1. Ingest Service

Отвечает за чтение входящих директорий:

- Sirena received-files
- FTP tickets
- FTP realizations
- FTP payments
- SMB inbox 1С

Важно:

- использовать не только `inotify`, но и проверку "файл стабилен и дописан";
- не обрабатывать файл, пока размер меняется;
- для каждого файла вычислять `sha256`.

### 2. Parser Service

Нормализует документы в общую модель.

Поддерживаемые типы:

- `ticket`
- `realization`
- `payment`

### 3. Delivery Service

Выполняет перемещение документов:

- из Sirena в FTP tickets;
- из FTP realizations в SMB;
- из SMB/FTP payments в MOM.

### 4. Tracking Service

Хранит историю статусов, ошибок, повторных попыток и времена этапов.

### 5. Backup Service

Делает снимки:

- оригиналов файлов;
- распарсенных метаданных;
- дампа БД;
- журнала событий;
- конфигурации системы.

## Статусы для красивой плашки

Для карточки билета можно строить шаги так:

1. `sirena_received`
2. `ticket_copied_to_ftp`
3. `ticket_seen_by_mom`
4. `realization_received_from_mom`
5. `realization_copied_to_smb`
6. `realization_accepted_by_1c`

Для платежки:

1. `payment_received_from_1c`
2. `payment_copied_to_ftp`
3. `payment_seen_by_mom`
4. `payment_processed_by_mom`

Каждый шаг должен хранить:

- статус;
- время начала;
- время завершения;
- длительность;
- комментарий;
- первоисточник сигнала.

## Связь между `ticket` и `realization`

### Вывод по текущим образцам

На бэкапе `2025-11-13` есть подтвержденная связь через `PNR`.

Прямого совпадения по номеру билета между просмотренными `ticket` и `realization` на этом срезе нет, но есть пересечения по `PNR`.

Это означает:

- связь есть;
- она не всегда строится по номеру билета;
- `realization` часто агрегирует несколько билетов одного бронирования.

### Пример из образцов

В `tickets` есть несколько файлов с PNR `7MBPRP`.

Они связываются с `realization`:

- `MOM-0007584`

То есть модель связи должна быть не только `1 ticket = 1 realization`, а:

- `many tickets -> one realization`
- иногда `one ticket -> many realization records` по повторной выгрузке/версии

### Рекомендуемая стратегия линковки

Приоритет правил:

1. Прямой match по номеру билета, если он есть в обеих сторонах.
2. Match по `PNR`.
3. Match по `PNR + passenger`.
4. Match по `passenger + route + issue/deal date`.
5. Match по `passenger + amount + близкая дата`.

Для каждой связи сохранять:

- правило, которым она построена;
- уровень уверенности;
- автоматическая или ручная привязка.

### Важный нюанс

Некоторые `realization` в образцах помечены как `deleted="true"` и не содержат финансовый документ.

Значит, в UI и логике нужно поддержать:

- актуальную версию документа;
- отмененные/удаленные реализации;
- несколько файлов для одного `MOM-number`.

## Как получать статусы по шагам

### Шаг 1. Sirena -> локальный контроль

Событие создается, когда файл появился в:

- `/opt/sirena-olt-client/received-files`

### Шаг 2. Локальный контроль -> FTP tickets

Событие создается после успешного копирования файла в:

- `/srv/ftp/tickets`

### Шаг 3. FTP tickets -> MOM

Если MOM забирает файл сам и прямого API нет, статус можно строить по косвенным признакам:

- файл исчез из входной папки или переместился в `processed` / `error`;
- появился связанный `realization`;
- есть запись в логах или служебный ответ MOM.

Если у MOM есть API или webhook, лучше использовать их как источник истинного статуса.

### Шаг 4. MOM -> FTP realizations

Событие создается при появлении XML в:

- `/srv/ftp/realizations`

### Шаг 5. FTP realizations -> SMB

Событие создается после успешного копирования на SMB-шару 1С.

### Шаг 6. Подтверждение 1С

Пока это отдельный необязательный этап.

Его можно сделать тремя способами:

- файл-ack от 1С;
- запись статуса в БД;
- возвратная платежка или другой технический XML.

## Бэкапы

Нужно хранить бэкап в формате по дате, например:

- `backups/2026-04-02/tickets/...`
- `backups/2026-04-02/realizations/...`
- `backups/2026-04-02/payments/...`
- `backups/2026-04-02/database/...`
- `backups/2026-04-02/manifests/...`

Что сохраняем:

- оригинальные XML;
- ошибки парсинга;
- копии логов;
- экспорт БД;
- JSON manifest со списком файлов, хэшами и метаданными.

## Интерфейс

Интерфейс должен быть операционным: не просто реестр XML, а рабочее место сотрудника.

### Главный экран

- счетчики по новым, успешным и ошибочным документам;
- время последней синхронизации;
- состояние интеграций Sirena / FTP / MOM / SMB / 1С;
- график активности по времени.

### Основная структура интерфейса

В веб-морде должно быть две отдельные вкладки:

- `Билеты и реализации`
- `Платежки`

Такое разделение обязательно, чтобы пользователь не смешивал два разных бизнес-потока.

### Вкладка `Билеты и реализации`

Это основной операционный экран.

Он показывает:

- билеты из Sirena;
- связанные с ними реализации MOM;
- текущий этап обработки;
- ошибки по доставке;
- времена выполнения шагов;
- связь `ticket -> realization`.

Основной режим отображения:

- список карточек или строк с быстрым статусом;
- открытие полной карточки по клику;
- видимость связанных реализаций прямо в строке или боковой панели.

### Вкладка `Платежки`

Отдельный экран для потока:

- `1С/SMB -> FTP(payments) -> MOM`

Он показывает:

- входящие платежки;
- направление обработки;
- статус отправки в MOM;
- ошибки обработки;
- журнал повторных попыток.

### Логика списка по умолчанию

По умолчанию пользователь должен видеть только:

- документы, которые еще обрабатываются;
- документы, обработанные с ошибкой.

Успешно завершенные документы по умолчанию скрыты из оперативного списка.

Это делает интерфейс рабочим, а не перегруженным архивом.

### Поведение ошибочных документов

Документ с ошибкой можно:

- открыть;
- изучить;
- пометить как просмотренный;
- скрыть из оперативного списка.

Важно:

- скрытие не удаляет ошибку;
- скрытие не удаляет документ;
- документ остается доступным через поиск, фильтры и историю;
- при необходимости его можно снова показать.

Рекомендуемое поведение:

- скрытие ошибки должно быть персональным для пользователя;
- администратор при желании может видеть все скрытые ошибки.

### Реестр документов

Фильтры:

- тип документа;
- номер билета;
- PNR;
- номер MOM;
- номер платежного документа;
- пассажир;
- ФИО;
- дата;
- период дат;
- статус;
- ошибка;
- клиент;
- направление потока.

Дополнительно нужны быстрые фильтры:

- `В работе`
- `Ошибка`
- `Скрытые`
- `Успешные`
- `За сегодня`
- `За 3 дня`
- `За 7 дней`
- `За период`

Поиск должен работать по следующим полям:

- ФИО пассажира;
- номер билета;
- номер обменного билета;
- `PNR`;
- номер `MOM`;
- номер платежного документа;
- назначение платежа;
- имя файла;
- клиент/контрагент.

### Просмотр за период

Обязательно должен быть режим просмотра всех документов за период.

Пользователь выбирает:

- дата начала;
- дата окончания;
- тип потока;
- статус;
- скрытые или не скрытые записи.

Это отдельный сценарий от оперативного списка.

### Карточка документа

В карточке билета:

- основные поля билета;
- найденный `PNR`;
- связанные реализации;
- связанные платежи;
- красивая плашка статусов;
- точные времена каждого шага;
- лог событий;
- исходный XML;
- ошибки и ретраи.

Дополнительно в карточке нужно показывать:

- откуда файл пришел;
- куда файл был отправлен;
- хэш файла;
- имя физического файла;
- все связанные документы;
- историю повторных доставок;
- кто скрыл ошибку и когда;
- итоговый технический результат обработки.

### Карточка `ticket -> realization`

Для связанного потока нужно делать красивую связанную плашку:

- билет;
- связанные реализации;
- шаги обработки;
- время каждого шага;
- текущий итог.

Если у одного билета несколько связанных реализаций или у одного `PNR` несколько билетов, UI должен показывать это явно, а не скрывать связь.

Рекомендуемый вариант:

- верхняя часть карточки показывает сам билет;
- ниже блок связанных реализаций;
- ниже таймлайн;
- ниже технические детали и XML.

### Вид плашки

Пример:

- `Sirena received`
- `Moved to FTP`
- `Processed by MOM`
- `Realization received`
- `Moved to 1C SMB`
- `Accepted by 1C`

У каждого шага:

- зеленая галочка, если успешно;
- красный статус, если ошибка;
- серый, если этап еще не наступил;
- время начала и завершения;
- длительность.

Рекомендуемые улучшения UX/UI:

- цветовая кодировка только по смыслу, без визуального шума;
- крупный человекочитаемый статус в шапке карточки;
- у каждого шага короткий текст результата;
- показ абсолютного времени и длительности одновременно;
- в списке сразу виден проблемный шаг;
- ошибки не прячутся в глубине карточки, а видны в строке списка;
- XML открывается в отдельной панели или вкладке;
- для длинных цепочек использовать горизонтальный stepper или вертикальный timeline;
- важные идентификаторы (`PNR`, номер билета, `MOM`) должны быть видны без открытия карточки;
- поиск и фильтры должны сохраняться в URL.

### Экран администрирования

Нужен отдельный раздел только для `admin`:

- список пользователей;
- создание пользователя;
- создание администратора;
- изменение роли;
- деактивация учетной записи;
- сброс пароля;
- журнал админских действий.

## Нефункциональные требования

- идемпотентность обработки;
- повторные попытки доставки;
- запрет дублирования по хэшу;
- аудит действий;
- разграничение доступа по ролям;
- безопасная работа с частично записанными файлами;
- понятный журнал ошибок;
- ручной перезапуск документа из UI.

## Что важно учесть в реализации

- один и тот же `MOM-number` может приходить несколько раз;
- у одного `PNR` может быть несколько билетов;
- `payment` не всегда относится к одному билету, часто к `MOM-number`;
- источником истины для связи нужно делать не имя файла, а извлеченные бизнес-ключи;
- событие "MOM успешно обработал" лучше подтверждать фактом появления связанного ответа, а не только перемещением файла.
